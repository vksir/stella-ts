# 技能：一个扩展承载，创建会话时定格

技能（skill）让 Stella 携带可复用的指令包：系统提示只放名字、描述与 `SKILL.md` 路径，正文由模型用 `read` 按需读取。格式沿用 Agent Skills 规范（与 pi / Claude Code 一致）。本 ADR 记录三个决定：谁承载、何时定格、开关落在哪。

## 问题

要加技能，有三组相互牵制的选择：

1. **承载方式**：每个技能一个扩展？一个扩展承载全部技能？还是写进主流程代码？
2. **清单何时生成**：每轮请求现扫目录，还是创建会话时生成一次？
3. **开关落在哪**：全局启用名单、预设白名单，还是会话级开关？

另有一个底层事实：Stella 用的 pi-durable 1.5.1 没有技能概念，但它的 `pi.agent.extensions` 按**名字**存储、运行时从注册表解析——这是唯一不需要改底层的挂载点。

## 决策

**一个扩展承载全部技能**：`server/src/extensions/skills/` 导出 `stella-skills` 扩展，负责扫描、解析、渲染系统提示里的 `<available_skills>` 段。每个技能不单独成为扩展——那样预设的 `extensions` 名单会混进几十个 `skill:*` 名字，实现细节泄漏进用户配置。

**创建会话时把清单定格**：扫描 `$STELLA_DATA_DIR/skills/`、按预设白名单过滤、渲染成字符串，写进会话文档 `SkillSnapshot`（`catalog` + `entries`）。`stella-skills` 的 section 每轮只返回这个字符串，**不读磁盘**。之后目录的增删改只影响新会话。

**开关落在预设**：`PresetDefinition.skills`（`null`/缺省 = 全部，`[]` = 全禁，数组 = 白名单）。管理页改写这个字段，写回 `data/stella.config.json`（读-改-写 + 同目录临时文件 rename）。没有全局启用态——预设是「这套会话能做什么」的唯一定义。

## 考虑过的替代方案

**每个技能一个扩展。** 预设的 `extensions` 会变成 `["stella-persona", "skill:pdf-tools", ...]`，用户配置里出现内部前缀；技能数量增长时注册表也跟着膨胀。唯一的好处是白名单可以免费复用扩展选择，但代价是把实现细节写进配置契约。

**每轮请求现扫目录。** 目录一变（新增技能、改一句描述），已有会话的系统提示就跟着变。系统提示与工具定义是模型请求的前缀，provider 的前缀缓存按它命中；变一个字就从那里开始全部重算。技能目录是用户随手会动的目录，这个代价必须避免。

**把清单拼进预设的 `instructions`。** 不需要新文档，但把机器生成的清单和用户手写的人设挤进同一个字段；且 `instructions` 是预设级静态字符串，拼进去之后「这个会话装了哪些技能」就没有独立的事实来源。

**全局启用名单 + 预设白名单两层。** 多一层「装了没装」的运维语义，但对单用户本机部署没有实际收益；`stella.config.json` 是唯一配置入口，预设已经表达了能力边界。

**用工具承载技能（每技能一个 tool 或 `skill()` 工具）。** 工具清单同样在请求前缀里，加载技能会改变工具集合，前缀缓存照样失效；几十个技能还会把工具声明撑大。技能是「一段按需读取的文字」，不是「一个新的可调用能力」。

## 后果

- **改技能开关只影响新会话。** 与预设的既有语义一致；已有会话的清单是它自己的事实。
- **删掉技能文件不会弄坏已有会话。** 会话只读快照，不读磁盘；只是 `/skill:<名字>` 读不到正文。
- **管理页必须写回 `stella.config.json`。** 这修订了 ADR-0002 的「从不写回」：部署字段仍只读，预设字段可由管理页写。写入用临时文件 + rename，避免 `fs.watch` 读到半截。
- **全选保存写 `null`。** 名单一旦显式化就冻结了当前集合，之后新增的技能默认是关的；写 `null` 保持「跟随全部」。
- **技能正文的读取走 `read` 工具。** `NodeExecutionEnv` 不限制绝对路径，技能目录可以直接读；`disable-model-invocation: true` 的技能不进清单，留给 `/skill:<名字>` 手动触发。
